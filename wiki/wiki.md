## Findings
- **Signature space ≈ 2 clusters (K=2):** arrest (cell-cycle-down) vs proliferation (DNA-replication-up). _[cell d8f3a0c7; config SIG_K]_
- **Arrest cluster** (~176 compounds): cell-cycle/mitosis + DNA-replication suppressed. Predictable from chemistry at a **real but modest** level — HistGB **roc_auc ~0.80** (vs other-active) → **~0.85** (vs whole library), pr_auc ~0.39, mcc ~0.24; baseline 0.79/0.32. _[autoresearch/predict_arrest_cluster: summary.md, best.json; cell c7b6e7c4]_
- **Adding inert (Single/Silent) as negatives raises roc_auc ~0.80→~0.85** — arrest chemistry is more separable from inert than from other-active, and better matches whole-library screening. _[campaign comp_* runs]_
- **DNA-replication-up cluster = coordinated proliferation program:** DNA replication + cell-cycle/mitosis + translation/ribosome + DNA-repair/HR up; adhesion / immune / lipid / transport down. "DNA replication up" is only the single top axis (auto-label = idxmax). _[GSEA NES lollipop; cell c7b6e7c4]_
- **Activity bins:** `Single (1)` + `Low (2-10)` merged → `Single/Low (1-10)`. **single/low is the *majority*** of the screened library (~60%, 1371/2277). _[cells 9daf56c9 / 9b42a6ce merge; ee227c90 classifier; MS.csv]_
- **Best simple arrest model:** `HistGradientBoostingClassifier(lr=0.03, max_depth=6, max_leaf_nodes=15, l2=0.0)`. _[campaign tune_his_24]_
- **Single/Low (ndown 1-10) vs all = WEAK chemical signal, ~0.68 ceiling, poor out-of-time.** Campaign (589 exp, FBX cohort 2,579 / 62.7% pos): champion `RandomForestClassifier(n_estimators=400, max_depth=24, max_features='sqrt', min_samples_leaf=4, class_weight='balanced_subsample')` on **Morgan bits only** → roc_auc **0.683** / pr_auc 0.763 / mcc **0.26** (dummy 0.504). The whole leaderboard is clustered 0.675–0.683 — **flat surface, family/features barely matter** (full 2,535-feature RF ≈ 0.678; AtomPair adds nothing; signal lives in Morgan substructure; physchem-only 0.614). **Temporal split (train pre-FBX → test FBX, n=1819→760) = roc_auc 0.590 / mcc 0.13 — a ~0.09 optimism gap; barely ranks on prospective compounds.** Verdict: real but weak, much softer than arrest (~0.80) and does not generalize out-of-time. **Reframings are far more separable** (non-primary tasks, compare via roc_auc): single/low vs *strong*-active (M+H) **0.750**, vs Silent **0.721**; whereas single-only-vs-all is ~chance (0.595) — the 1-10 band is chemically intermediate, so "vs all" (silent+strong on both sides) is the hardest framing. **DECISION (2026-06-23): deploy with full H236 features, NOT the Morgan-only champion** — on the time-based split (cell `65229a7e`) the Morgan-only champion was *slightly worse* than full H236, i.e. the Morgan edge was a random-CV artifact that didn't hold prospectively. _[autoresearch/optimize_SingleLow_Classification: summary.md, best.json; cells 65229a7e / cb16782f]_
- **Multiclass chemistry→activity: merging Single+Low predicts better than splitting them.** (2026-07-08, cell `9b42a6ce`; random 5-fold CV, RF `class_weight='balanced'`, full H236 feats — optimistic / analog-leak.) 4-class (Single/Low **grouped**, n=2141): merged class ROC_auc **0.66** / F1 **0.77** / PR_auc **0.74**, macro ROC_auc 0.71. 5-class (**split**): **Single (1) ROC_auc 0.58 (~chance)**, Low (2-10) 0.63, macro ROC_auc 0.68. **Why:** the 1-vs-2 cutoff is a noisy threshold on a low degradation count near the assay's detection floor, not a distinct chemical phenotype — chemistry can't resolve Single from the similar Low, so splitting adds label noise, halves class mass, and dilutes each one-vs-rest contrast; merging restores a coherent, well-powered "any low responder (1-10)" class. Corroborates the earlier *single-only-vs-all ≈ chance (0.595)* result → **keep Single+Low merged**. Silent/Medium/High ~unchanged across both (Medium near-unlearnable, F1 0.02-0.05, n=186; High best-separated, ROC_auc 0.79-0.80). Caveat: macro metrics aren't strictly comparable across 4 vs 5 classes — the like-for-like signal is merged-class AUC (0.66) > either split AUC (0.58 / 0.63). _[cell 9b42a6ce; helper `ML_Class.run_K_Fold_Xval_multiclass_Classification`]_
- **The 17K enumeration is mostly OUT of the [1-12] model's applicability domain → its high `proba_low` are extrapolation, not signal.** (2026-07-16, `MS_ML_Prioritization` enum-vs-training-space cell; `Px_activity_1_12` MLTrail model, binary Morgan-2048 NN Tanimoto distance.) Enum→training NN distance peaks ~0.36 vs training's own internal NN spread peaking ~0.19; the bulk of the enum sits **beyond the training 95th-pct NN distance (~0.33 "domain edge")**. Worse, enum `proba_low` **rises with distance to training** (near neighbours ~0.5-0.65, far cloud ~0.65-0.80, centred ~0.68 ≈ the ~67-71% positive base rate) — the shallow HGBC regressing toward the positive prior where it has no nearby support. So the ~1,300 enum "hits" at `proba_low>0.75` are largely **manufactured by the prior**, and the temporal validation (which only reached dist ≤0.4, mostly ≤0.25, with *flat* confidence) does **not** cover this regime. **DECISION: gate enum prioritization by applicability domain — trust `proba_low` only within ~0.33 (ideally ≤0.25) NN Tanimoto of training; treat out-of-domain high-proba as "can't say", not "active".** Corroborates the temporal-test AD check (in-domain, dist ≤0.4, confidence flat vs distance). _[MS_ActivityClass "check chemical distance vs confidence" cell; MS_ML_Prioritization "compare enum's chemical space distance to training" cell; `nn_tanimoto_dist` chunked-matmul helper]_

## Dropbox access (rclone by default; SSH tunnel as fallback)
The `config.yaml` path keys (`PATENTS_RAW`, `PX_*`, `DROPBOX_*`, `FBX_DIR`, `ENAMINE_*`, `STOCK_INVENTORY`) are absolute WSL paths where the **laptop's Dropbox desktop client** keeps files synced. Two backends can read them from the cluster, selected by **`DROPBOX_BACKEND`** in `config.yaml`; both stream into memory and **write nothing to the cluster disk**. The notebooks' params cell binds `_dbx` / `_fbx_open` / `_fbx_glob` to the chosen backend, so **every `pd.read_csv(_dbx(PATH))` call site is backend-agnostic**.

**`rclone` (default, 2026-08-10) — no laptop, no tunnel.** `fn.open_rclone` / `pull_rclone` / `glob_rclone` / `push_rclone` (`rclone cat` / `lsf` / `rcat`) pull straight from Dropbox via the pre-authenticated `dropbox:` remote, so they work with the laptop off/asleep — this **removes the whole zombie-tunnel failure mode**. `fn._rclone_target` maps a host path to a remote one by stripping `DROPBOX_LOCAL_ROOT` (`/mnt/c/Users/gtamo/Serac Biosciences Dropbox/`) and prefixing `DROPBOX_REMOTE` (`dropbox:`), collapsing any `//` from path concatenation and raising if the path isn't under the root — so **`config.yaml` paths stay unchanged**. **Gotcha:** the account is a Dropbox *Business* team, and `Serac_team` lives in the **team namespace** (`14101584243`), not the member's home namespace (`14097138451`) — without `root_namespace` set, `dropbox:` shows only the personal space and every `Serac_team/...` path 404s. Set once in `~/.config/rclone/rclone.conf` (`root_namespace = 14101584243`); edit the file directly — `rclone config update` tries to re-run the OAuth flow (needs a browser) and hangs. Verified 2026-08-10: reads the 1,044-row deliverable CSV and discovers all 9 FBX tranche dirs, matching the ssh backend.

**`ssh` (fallback) — reverse tunnel to the laptop's mirror.** `fn.pull_from_dropbox` / `open_dropbox` / `push_to_dropbox` / `glob_dropbox(dir, pattern)` stream over ssh (the remote shell expands the glob), path passed **verbatim**. Kept for when rclone/network is unavailable; see the topology + setup below. **Known failure mode:** if the laptop-side ssh dies, the cluster's port stays `LISTEN`ing with sockets in `CLOSE-WAIT` and new connections hang at *"Connection timed out during banner exchange"*. The listener is owned by the **root sshd** and is **not killable from the cluster** (socket-inode correlation shows no user-owned PID holds it); fix from the **laptop**: `pkill -f '2222:localhost:22'` then re-establish. If reconnect gives *"remote port forwarding failed for listen port 2222"*, the stale listener isn't reaped yet — use `2223` and set `DROPBOX_SSH_PORT`. Prevent it with `-o ServerAliveInterval=30 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes`.

**Topology:** you sit at the WSL laptop and ssh *into* the cluster, but the pull needs the cluster to reach *back* to the laptop. So the cluster→laptop hop rides a **reverse tunnel** on your connection. (WSL2 is NAT'd behind Windows, so a direct inbound connection to WSL's sshd would need Windows port-proxying; the reverse tunnel avoids that.)

**One-time setup**
1. **Laptop (WSL): run an SSH server** — `sudo apt install -y openssh-server; sudo ssh-keygen -A; sudo service ssh start`. Use WSL's sshd (**not** Windows OpenSSH) so `/mnt/c/...` paths + `cat` work in bash.
2. **Key auth cluster→laptop** — append the cluster's `~/.ssh/id_ed25519.pub` to the laptop-WSL `~/.ssh/authorized_keys` (`chmod 600`).

**Each work session**
3. **Open the reverse tunnel from a WSL terminal on the laptop** (keep open while pulling): `ssh -R 2222:localhost:22 gtamo@<cluster>`. Alternatives: add `RemoteForward 2222 localhost:22` to `~/.ssh/config`; or a dedicated `ssh -R 2222:localhost:22 -N gtamo@<cluster>` side-session (use this if VS Code Remote-SSH uses the Windows ssh client, whose RemoteForward wouldn't hit WSL's sshd).
4. **Point the functions at the tunnel** — config is set to `DROPBOX_SSH_HOST: gtamo@localhost` / `DROPBOX_SSH_PORT: 2222`, but the functions read the host from **`$DROPBOX_SSH_HOST`** (or a `host=`/`port=` arg), NOT the YAML. So `export DROPBOX_SSH_HOST=gtamo@localhost DROPBOX_SSH_PORT=2222` before Jupyter, or bridge in the params cell: `os.environ['DROPBOX_SSH_HOST']=DROPBOX_SSH_HOST; os.environ['DROPBOX_SSH_PORT']=str(DROPBOX_SSH_PORT)`.

**Use**
```python
import functions as fn
df  = fn.pull_from_dropbox(DROPBOX_VALIDATION)              # csv/tsv/xlsx/parquet → DataFrame
df  = fn.pull_from_dropbox(PX_20260529_DB, usecols=[...])  # trim big files (this one ≈ 479 MB → full load ~1–2 GB RAM)
buf = fn.open_dropbox(ENAMINE_20260513)                    # other types → io.BytesIO (feed .sdf to RDKit)
fn.push_to_dropbox(df, DROPBOX_ML + '/out.csv')            # DataFrame/bytes/file → host; Dropbox client syncs it up
```
**Gotchas:** tunnel must be up during pulls (close the session → port 2222 gone → connection error); `pull_from_dropbox` loads the whole file into RAM (pass `usecols`/`nrows`/`dtype` to trim); `push_to_dropbox` writes into the company Dropbox — mind the data-privacy rules for derived data.
